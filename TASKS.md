## T-001 — Диагностика двух llama-server

**Статус:** PLANNED  
**Приоритет:** HIGH

Провести read-only аудит двух отдельных серверов:
- Hermes llama-server — ожидаемый адрес `127.0.0.1:18434`.
- Unsloth / Claude Code llama-server — последний подтверждённый в рабочей сводке адрес `127.0.0.1:52681`; порт динамический, требуется перепроверка.

Проверить процессы/PID/командные строки/пути к бинарным файлам; фактические GGUF и параметры запуска; слушающие порты и HTTP API; VRAM/RAM; серверный контекст (`n_ctx` / `--ctx-size`) и KV cache; маршрутизацию и авторизацию; логи ошибок и обрывы соединения.

**Ограничения:** не объединять серверы; не останавливать процессы, не перезапускать службы и не менять конфигурации в рамках аудита. Исторические значения портов не считать гарантированно текущими. Не публиковать API-ключи и другие секреты.

**Результат:** таблица процессов и портов, подтверждённая схема маршрутизации, факты отдельно от гипотез, конкретная последовательность исправлений.

## T-002 — Настройка контекста Claude Code / Unsloth и Auto-Compact

**Статус:** PLANNED  
**Приоритет:** HIGH

Цель: получить максимально большой **стабильный** контекст Qwen3.5-9B на RTX 3060 12 GB и уменьшить частоту автоматической компактизации Claude Code.

Проверить до изменений: версию Claude Code; фактический контекст клиента (`/context`); серверный контекст и `n_ctx`; настройки Auto-Compact; точные названия и поддержку параметров в установленной версии Claude Code; VRAM/RAM и KV cache; соответствие лимита клиента реальному лимиту сервера.

Затем предложить и согласовать безопасную конфигурацию. Не отключать Auto-Compact вслепую и не задавать клиенту лимит выше фактически поддерживаемого сервером. Не снижать установленное требование пользователя: контекст не менее 40K без отдельного согласования; ранее обсуждавшаяся цель — 160K, но её достижимость нужно доказать измерениями на этой машине.

**Результат:** проверенные значения, обоснованный целевой контекст, настройки клиента и сервера, тест на длинном диалоге и подтверждение, что компактизация происходит реже без ошибок переполнения.

## T-004 — Устранить частую компактизацию Claude Code (Auto-Compact thrashing)

**Статус:** INVESTIGATE  
**Приоритет:** HIGH

Зафиксированный симптом из текущего сеанса Claude Code:
> Autocompact is thrashing: the context refilled to the limit within 3 turns of the previous compact, 3 times in a row.

Во время аудита Claude Code успел прочитать:
- `.claude.json`;
- файл с API-ключом Unsloth (секрет; содержимое не копировать и не публиковать);
- `~/.hermes/runtimes/llamacpp/server.json`;
- `~/.hermes/runtimes/llamacpp/presets.ini`;
- `QWEN_AUDIT_REPORT.md` (385 строк).

Проверить гипотезы, не выдавая их за установленные причины:
1. Чрезмерно большие результаты чтения файлов и вывода инструментов.
2. Реальный размер контекста, доступный Claude Code, меньше ожидаемого.
3. Несовпадение лимитов клиента Claude Code и сервера Unsloth/llama-server.
4. Порог Auto-Compact и поведение конкретной версии Claude Code.
5. Расход контекста системными инструкциями, историей и содержимым tool outputs.

Нужно установить:
- фактический размер окна по `/context`;
- версию Claude Code и поддерживаемые именно ею параметры;
- текущий порог Auto-Compact и относящиеся к нему переменные окружения/настройки;
- серверный `n_ctx` / `--ctx-size`, KV cache и доступную VRAM/RAM;
- какие именно tool outputs привели к резкому росту контекста, если это можно подтвердить.

Порядок: сначала сохранить промежуточный отчёт; затем продолжить аудит короткими порциями, не читая большие файлы целиком; только после подтверждения причин предложить изменения. Не отключать Auto-Compact вслепую и не задавать клиенту контекст выше серверного.

**Результат:** отчёт с измерениями, доказанными причинами и безопасным планом настройки.

## T-005 — Проверить архитектуру одного llama-server с несколькими slots для двух агентов

**Статус:** RESEARCH  
**Приоритет:** VERY HIGH

**Новая рабочая гипотеза пользователя:** возможно, не нужны две одновременно загруженные копии Qwen. Один экземпляр модели и один llama-server могут обслуживать несколько агентов через параллельные slots. Нужно проверить это на текущей связке Hermes + Claude Code + Unsloth, прежде чем выполнять общий тюнинг.

### Что уже известно из предыдущего аудита (требует сверки с актуальной конфигурацией)

- Hermes llama-server ранее запускался отдельно на `:18434`, с контекстом около 98K.
- Unsloth llama-server для Claude Code ранее имел `--parallel 4`, `-c 65536`, `--kv-unified`, `--slot-save-path` и `--ctx-checkpoints 5`.
- Следовательно, Unsloth уже был настроен на четыре параллельных server slots. Это само по себе не доказывает, что два независимых агента действительно использовали два слота одновременно.
- Ранее Hermes и Claude Code работали параллельно, но каждый был направлен на отдельный сервер/endpoint. Нужно выяснить, работали ли они одновременно на одной загруженной модели или использовали две копии Qwen.

### Проверить по документации и исходному коду именно установленных версий

1. Что именно означает `--parallel N` / `n_parallel` в текущей сборке llama.cpp и Unsloth Studio.
2. Как распределяется `--ctx-size` между слотами в этой версии; не предполагать, что `-c 65536` означает 65K на каждый из четырёх слотов.
3. Поддерживает ли текущая сборка `--kv-unified-per-slot`; как он взаимодействует с `-c`, `--parallel` и KV cache.
4. Как Unsloth Studio передаёт число slots через поле `n_parallel`, и не уменьшает ли VRAM fitter фактическое число slots.
5. Как API-запросы автоматически занимают свободные slots; есть ли реальная возможность закрепить агента за отдельным slot или распределение динамическое.
6. Можно ли подключить одновременно Hermes и Claude Code к одному endpoint без конфликтов API-формата, ключей, system prompt, chat template и истории сессий.
7. Сколько VRAM/RAM требует один слот и два активных слота при фактическом контексте; отдельно проверить одновременную генерацию и длинный prefill.
8. Что произойдёт, если оба агента одновременно отправят длинные запросы; проверить очередь, latency, throughput, контекстное переполнение и сохранение изоляции разговоров.

### План безопасного эксперимента

- Сначала read-only аудит текущих процессов, версий, параметров и endpoint.
- Не запускать вторую копию модели.
- Не менять текущую работающую конфигурацию до сохранения baseline.
- Проверить один сервер с двумя короткими параллельными тестовыми запросами и наблюдать `/slots`, VRAM, RAM, latency и логи.
- Затем, только если тест успешен, проверить реальных двух клиентов (Hermes и Claude Code) на одном endpoint, с разными сессиями/историями.
- Не считать два агента изолированными только потому, что сервер показывает два slots: проверить отсутствие смешивания prompt/history и tool calls.
- При нехватке памяти уменьшить число slots или per-slot context на основании измерений; не менять модель и не удалять конфигурации.

### Критерий успеха

Один процесс llama-server, одна загруженная копия Qwen3.5-9B, два независимых клиента/агента, два одновременно обслуживаемых запроса, изолированные истории, стабильная VRAM/RAM и отсутствие ошибок контекста/соединения.

**Важное уточнение терминологии:** в официальной документации llama.cpp это называется parallel slots / `--parallel`, а не “OnSlot”. Необходимо уточнить, не имел ли пользователь в виду именно механизм slots.

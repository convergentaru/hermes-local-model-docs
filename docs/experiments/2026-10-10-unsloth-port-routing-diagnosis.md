# Диагностика: Unsloth API и динамический порт llama-server

Дата: 2026-10-10. Статус: ложное срабатывание диагностики; не менять конфигурацию по этому признаку одному.

## Что заметил Hermes

Локальная проверка сформулировала проблему примерно так:

- конфигурация Hermes использует provider Unsloth (адрес Studio/API, порт 8888);
- процесс llama-server слушает отдельный порт (в последнем сообщении агента — 41879);
- агент предложил переключить Hermes с Unsloth на прямой llama-cpp.

Затем попытка изменения завершилась сообщением вида `Stream stalled mid tool-call (patch); the action was not executed`. Это значит, что данный patch не был выполнен; перед дальнейшими правками нужно заново проверить фактические настройки, не исходить из предположения, что файл уже изменён.

## Что уже известно из фактических проверок

1. Unsloth Studio ранее слушал порт 8888. Запрос к `http://127.0.0.1:8888/v1/models` без авторизации вернул `Not authenticated`.
2. Unsloth Desktop был настроен на пользовательский runner: `/home/oleg/llama.cpp/build-cublas/bin/llama-server`.
3. После загрузки Qwen3.5-4B процесс `llama-server` работал на динамическом порту 36679; модель отвечала в UI и показала `UNSLOTH_CUDA_TEST_OK`.
4. Команда `unsloth start hermes --app` была выполнена.
5. Визуальный Hermes после подключения вернул `HERMES_UNSLOTH_OK`.

В другой диагностической реплике указан backend port 41879. Порт может изменяться между загрузками, поэтому не считать один из номеров фиксированным.

## Вывод

Unsloth Studio/API entry и управляемый им llama-server worker могут работать на разных портах. В этом стеке это ожидаемая архитектура: Studio предоставляет защищённый API/proxy, а llama-server обслуживает конкретную загруженную модель. Различие 8888 и 36679/41879 **само по себе не является ошибкой конфигурации**.

В публичном репозитории Unsloth также описан сценарий, где Studio на 8888 управляет llama-server на отдельном localhost-порту и сервер остаётся отдельно проверяемым: https://github.com/unslothai/unsloth/issues/9901. Это подтверждает, что раздельные порты используются, но не доказывает детали каждой установки — для нашей установки основное подтверждение даёт успешный тест Hermes.

## Как проверить корректно

1. Спросить, работает ли короткий текстовый запрос в Unsloth Desktop.
2. Проверить текущий процесс: `pgrep -af llama-server`. Записать текущий динамический порт.
3. Проверить в Hermes, какой provider/model выбран, не выводя секретные параметры.
4. Если `HERMES_UNSLOTH_OK` отвечает в новой сессии, оставить маршрут Unsloth.
5. Если новый запрос реально не проходит, диагностировать точную ошибку и авторизованный API route, а не переключать provider только ради совпадения портов.
6. Не использовать анонимный запрос к защищённому `/v1/models` как единственное доказательство неисправности.
7. При необходимости менять конфигурацию — сначала сделать резервную копию и попросить подтверждение пользователя.

## Решение для skill

Не выполнять автоматически следующие действия только на основании разных портов:
- заменять provider Unsloth на direct llama-cpp;
- подставлять динамический backend port в конфигурацию Hermes;
- удалять API key / auth;
- перезаписывать весь `config.yaml`.

Сначала подтвердить фактическую ошибку. Если API-цепочка работает, сообщить, что маршрут исправен, а диагностическое предположение было ошибочным.

# Единая память: ChatGPT ↔ Hermes ↔ GitHub

Статус: ACTIVE  
Назначение: главный рабочий протокол для локальной AI-инфраструктуры и связанных проектов пользователя.

## Источник истины

Для локального AI-стека главный источник проверяемой проектной информации:
`convergentaru/hermes-local-model-docs`.

Для остальных проектов использовать их собственные существующие GitHub-репозитории. Не сваливать несвязанные проекты в один репозиторий. ChatGPT Memory помогает сохранять пользовательские предпочтения и ключевые ориентиры, но не заменяет журнал. Локальные конфиги показывают фактическое состояние машины. GitHub хранит согласованную документацию и историю решений.

## Обязательные правила

1. Перед продолжением старой задачи прочитать актуальные bootstrap/state/next-action файлы соответствующего проекта и относящиеся к задаче документы.
2. Не просить пользователя повторять сведения, уже зафиксированные в репозитории или текущей переписке.
3. Не выдавать историческую конфигурацию за текущую. У каждой настройки должны быть дата и статус.
4. Не называть команду рабочей, пока она не выполнена и результат не подтверждён.
5. Не менять несколько слоёв одновременно. Один шаг → один тест → запись результата.
6. После каждого значимого результата обновлять журнал и текущее состояние соответствующего GitHub-репозитория.
7. При ошибке записывать точную команду, полный текст ошибки, дату и что именно было проверено. Не повторять заведомо неудачную команду без изменения причины.
8. Сначала читать и проверять существующие файлы и настройки; не создавать параллельные проекты и не переустанавливать то, что уже работает.
9. Сохранять рабочие конфигурации до изменений. Любая модификация конфигурации должна иметь резервную копию.
10. Не публиковать API-ключи, токены, пароли, приватные адреса, содержимое secret-файлов и другие чувствительные данные.

## Правило фиксации всей существенной работы

Пользователь поручил вести рабочую историю на GitHub. Это постоянное правило для всех проектов и последующих рабочих сессий.

Фиксировать не только финальный результат, но и существенный ход работы, чтобы задачу можно было продолжить без повторного сбора контекста:
- цель и исходные условия;
- принятые решения и причины;
- точные команды и действия, которые действительно выполнялись;
- фактические результаты, ошибки и неудачные попытки;
- изменения файлов и конфигураций, резервные копии;
- ограничения, неизвестные факты и нерешённые вопросы;
- следующий конкретный шаг;
- важные уточнения и исправления пользователя.

Вести запись в репозитории именно того проекта, к которому относится задача. Интеграционные изменения локального AI-стека можно дополнительно отражать здесь, в `hermes-local-model-docs`, но проектные материалы PC Rescue, Screenlife и других самостоятельных проектов не следует смешивать без необходимости.

Не записывать каждую бытовую реплику дословно. «Всё» означает полную и пригодную для восстановления историю существенной проектной работы, включая промежуточные факты и ошибки, а не стенограмму чата.

После значимого этапа:
1. Добавить датированную запись в журнал проекта.
2. Обновить текущий статус/bootstrap, если изменилось состояние.
3. Обновить список задач/следующее действие.
4. Обновить README или индекс, если появился новый важный документ.
5. Проверить, что GitHub действительно принял изменения; сообщить пользователю ссылку на запись или commit.

Если подходящий репозиторий известен и доступен, не оставлять результат только в чате. Если подходящего репозитория нет или GitHub недоступен, честно сообщить об этом и сохранить материал локально только при наличии соответствующего инструмента/доступа; не утверждать, что запись опубликована.

## Статусы достоверности

- `VERIFIED` — команда или настройка проверена на машине; результат зафиксирован.
- `OBSERVED` — наблюдалось в процессе или логе, но полного теста нет.
- `FAILED` — проверено и завершилось ошибкой.
- `PLANNED` — намерение или следующий шаг, ещё не выполнено.
- `SUPERSEDED` — историческая настройка, заменённая более новой.
- `UNKNOWN` — состояние не установлено.

Не повышать статус без нового фактического теста.

## Протокол начала каждой сессии

1. Если агент работает в этом репозитории, учитывать автоматически загруженный `AGENTS.md`.
2. Прочитать `SESSION_BOOTSTRAP.md` — единый свежий снимок состояния и незавершённой задачи.
3. Прочитать этот протокол, `CURRENT_STATE.md` и `NEXT_ACTION.md`.
4. Прочитать соответствующие инструкции конкретного компонента/проекта.
5. Сверить важные runtime-факты с текущей машиной только необходимыми read-only проверками.
6. Продолжить с указанного следующего действия. Не повторять завершённые этапы.

## Протокол после каждого достижения

Добавить запись в журнал проекта:
- дата;
- цель;
- точная команда или действие в GUI;
- параметры;
- фактический результат;
- статус;
- что осталось неизвестным.

Если изменилась рабочая конфигурация, обновить файл известных конфигураций и текущее состояние. Если изменился следующий шаг — обновить список задач и `NEXT_ACTION.md`. Если принято архитектурное решение — добавить его в журнал решений.

## Разделение ролей

- ChatGPT: анализ, план, контроль последовательности, проверка документации и фиксация результатов в GitHub.
- Hermes: локальное выполнение задач и сбор фактов с машины; отчёт должен содержать реальные команды и результаты.
- Ubuntu: источник фактического состояния процессов, файлов, моделей, памяти и сервисов.
- GitHub: общий долговременный журнал и согласованная документация.

## Минимальный формат отчёта Hermes

```text
TASK:
DATE:
STATUS: VERIFIED | OBSERVED | FAILED | BLOCKED | UNKNOWN
CHANGES:
COMMANDS:
RESULTS:
FILES_CHANGED:
BACKUPS:
RISKS / UNKNOWN:
NEXT_ACTION:
```

Hermes не должен писать `VERIFIED`, если он только создал конфиг или запустил процесс без успешного функционального теста.

## Восстановление после потери контекста

Если новая сессия не знает, что происходило:
- не начинать диагностику с нуля;
- открыть state/bootstrap, журнал и next-action нужного проекта;
- найти последнюю запись по нужной задаче;
- проверить только факты, которые могли измениться с момента записи;
- продолжить с незавершённого действия.

## Область действия

Этот протокол задаёт общий способ совместной работы. Для локального AI-стека он применяется к Unsloth Desktop/Studio, GGUF-моделям, llama.cpp, Hermes, Claude Code, OpenCode, jcode и связанным инструментам. Для всех остальных проектов вести отдельную память в соответствующих GitHub-репозиториях. Документация отдельных проектов (например, PC Rescue и Screenlife) остаётся в своих проектах/разделах; сюда заносится только интеграционная информация, необходимая для общей инфраструктуры.

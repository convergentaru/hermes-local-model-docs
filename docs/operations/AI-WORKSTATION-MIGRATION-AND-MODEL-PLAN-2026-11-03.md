## Очерёдность — не менять без нового решения пользователя

### 0. Закончить текущую проверку SystemRescue

- Сначала получить фактический отчёт Claude Code по уже запущенному QEMU-тесту.
- Не запускать повторный тест и не создавать параллельную тяжёлую нагрузку, пока не установлен результат текущего прогона.
- Отделять результаты QEMU от физической проверки USB: успешный QEMU-тест не доказывает успешную загрузку на реальном компьютере.

### 1. БОЕВАЯ ЗАДАЧА №1 — подготовить клиентскую USB-флешку SystemRescue 13.02

Выполнить и довести до проверенного результата текущую задачу подготовки Rescue USB.

Обязательные правила:
- Claude Code — основной исполнитель.
- Hermes — независимый проверяющий и аудитор, не основной исполнитель.
- Для записи USB использовать только согласованный штатный официальный SystemRescue USB Writer.
- Не переходить на `dd`, самодельные скрипты записи или альтернативные writer-инструменты при первой же проблеме.
- Если штатный writer не сработал — остановиться, сохранить полный лог и точную причину, доложить пользователю. Альтернативный способ допустим только после отдельного явного согласования.
- Сохранять протоколы как успешных, так и неуспешных записей: версия writer, исходный ISO и SHA-256, точная модель/устройство USB, выбранные параметры, время, полный лог, результат и последующая проверка.
- Сначала завершить текущий QEMU-тест и сверить его артефакты; затем выполнить физическую проверку на USB.
- Проверить фактическую загрузку, автоматический запуск X/StartX (если он предусмотрен конфигурацией), сетевое подключение и согласованные каналы удалённого доступа. Не считать функцию проверенной только по наличию настройки.
- Сохранить исходный SystemRescue 13.02 ISO как эталон. Не удалять исходник и не удалять артефакты без сверки и отдельного разрешения.
- Состояние перевода русской документации сверить по фактическим файлам, именам, размерам и контрольным суммам. Продолжать перевод с места остановки, не перезаписывая исходники и уже готовые результаты.

Связанные документы и активные задачи находятся в репозитории `convergentaru/pc-rescue-platform`; перед исполнением Claude Code должен прочитать актуальные README, NEXT ACTION/issue и профильные протоколы. В частности, учитывать текущие Reverse SSH / Tailscale / comparative USB workstreams и не смешивать их артефакты.

**Критерий завершения:** есть физически проверенная USB-флешка, воспроизводимая процедура записи штатным writer, сохранённые логи и доказательства загрузки/работы согласованных функций; перевод и его фактический статус зафиксированы.

### 2. Подготовить резервную копию перед переустановкой

Начать только после завершения боевой USB-задачи.

Внешний HDD/SSD для резервирования имеется.

Порядок:
1. Провести read-only инвентаризацию диска, HOME, проектов, моделей, конфигураций, пользовательских служб и системных настроек.
2. Составить manifest: что копируется, размер, источник, назначение, контрольная сумма и категория (обязательно / восстановить из GitHub / можно скачать заново / временное).
3. Сохранить пользовательские данные и важные конфигурации: проекты и Git-репозитории, документы, SSH-конфигурацию и ключи, Hermes и его skills/config/state, Claude Code config/state, Unsloth-профили, llama.cpp custom build/config, модели, скрипты, systemd user units, i3 и сетевые настройки.
4. Секреты, API-ключи и приватные ключи хранить только в защищённой резервной копии; не помещать их в GitHub и обычные текстовые отчёты.
5. Не копировать бездумно весь кэш, временные build-каталоги и воспроизводимые virtualenv. Решение по каждому крупному каталогу принять по инвентаризации.
6. Сделать контрольные суммы и проверить чтение резервной копии; выборочно восстановить несколько важных файлов в отдельное место.
7. Полный образ всего системного диска — необязательный дополнительный вариант. Сначала оценить объём и пользу; он не заменяет отдельную проверенную копию важных данных.

**Запрет:** не форматировать и не переустанавливать внутренний SSD, пока копия не проверена и пользователь явно не подтвердил готовность к установке.

### 3. Переустановить ОС: Ubuntu Server + графика по требованию

**Согласованная целевая схема:** Ubuntu Server 26.04 LTS, минимальная установка без GNOME/KDE и без автоматического запуска графической сессии.

Компоненты:
- NVIDIA proprietary driver и совместимый CUDA Toolkit;
- Unsloth как управляющий слой для одной общей локальной модели / одного inference server;
- Hermes и Claude Code как независимые клиенты одной модели;
- SSH включён постоянно для удалённого управления;
- Xorg + i3 + Polybar + Alacritty установлены, но по умолчанию не запущены;
- графическую сессию запускать вручную по требованию и корректно завершать, не останавливая inference/агентов;
- Chrome устанавливать только если он нужен в локальной графической сессии;
- не устанавливать GNOME/KDE и не добавлять Docker/контейнерный слой без конкретной необходимости.

Архитектурные ограничения:
- одна загруженная копия модели и один общий Unsloth-managed inference server; не возвращаться к двум независимым llama-server без отдельного решения;
- Claude Code — основной исполнитель программных задач;
- Hermes — диспетчер/проверяющий и коммуникационный агент, не дублировать им тяжёлую работу Claude;
- учитывать, что при текущем подтверждённом `--parallel 1` запросы клиентов обслуживаются последовательно, а не параллельно;
- не обещать отсутствие OOM только за счёт смены дистрибутива: отдельно измерять RAM, swap, VRAM, KV cache и нагрузку;
- настроить службы и расписание только после проверки фактического поведения после холодной загрузки.

**Режимы работы:**
- дневной: Hermes доступен как диспетчер; не держать тяжёлую генерацию без необходимости;
- ночной: выделенное окно для Claude Code и длительных задач; тяжёлые процессы запускать последовательно;
- тестовый: QEMU и физические испытания в отдельное окно, без конкурирующей сборки/генерации;
- запуск следующей тяжёлой задачи должен учитывать фактические RAM/swap/VRAM и статус предыдущей, а не только часы на расписании.

### 4. Исследовать Colibri и большие модели для совместной работы с Claude Code

**Статус:** RESEARCH / NOT INSTALLED.

- Установку, если она оправдана, сначала выполнить без автозапуска. Запускать только после отдельной проверки совместимости и ресурсов.
- Исследовать сценарий качественного кодинга с большой моделью, работающей совместно с Claude Code; не считать заранее, что требуется 27B.
- Сформировать короткий shortlist моделей класса примерно 14B–20B, а также рассмотреть промежуточные варианты. Учитывать не только число параметров и размер GGUF, но и квантование, архитектуру, KV cache, реальный контекст, CPU/RAM offload, VRAM и поддержку tool calling.

- Цель — более качественный результат и планомерная работа, даже если скорость ниже. Не запускать две большие модели одновременно на текущем оборудовании без отдельного расчёта и согласования.

Термин «Colibri» пока не подтверждён как точное имя продукта/репозитория в этом плане. Не подменять его автоматически Xiaomi MiMo или SoloEngine.

### 5. Исследовать панель управления агентами — после стабилизации базовой системы

- Hermes Studio — первый лёгкий вариант для визуального отображения ролей, задач, процессов и результатов.
- Paperclip — кандидат на следующий уровень оркестрации, если Hermes Studio окажется недостаточно.
- Xiaomi MiMo / SoloEngine — отдельное исследование; не подключать к текущей архитектуре до проверки.
- На MVP-этапе достаточно видеть: задача → исполнитель → статус → контрольная точка → отчёт → проверка.
- Не устанавливать несколько конкурирующих оркестраторов одновременно.
- Любая автоматизация должна иметь pause/stop, журналирование, восстановление с checkpoint и понятные ограничения на запуск тяжёлых задач.

## Правила исполнения и отчётности

- Один шаг → один результат → проверка → запись в GitHub.
- Пользователю давать по одному короткому терминальному блоку за раз; не присылать длинные диагностические простыни.
- Не начинать следующий этап, пока предыдущий не имеет понятного статуса.
- Отделять VERIFIED / OBSERVED / FAILED / PLANNED / UNKNOWN.
- Не утверждать, что файл, USB, резервная копия, настройка или тест готов, пока это не подтверждено.
- После каждого значимого этапа обновлять NEXT_ACTION, CURRENT_STATE и журнал в соответствующем репозитории.
- Никаких разрушительных действий и переустановки без явного подтверждения пользователя.

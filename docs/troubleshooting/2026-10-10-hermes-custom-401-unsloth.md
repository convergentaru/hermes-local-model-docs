# Инцидент: Hermes Desktop Custom возвращал HTTP 401 при работающем Unsloth

**Дата:** 2026-10-10  
**Результат:** восстановлено; после исправления переменной окружения и полного перезапуска Hermes Desktop ответил `HERMES_RECOVERY_OK`.

## Симптом

В Hermes Desktop появлялось сообщение:

- `Custom rejected your API key`
- `HTTP 401: Invalid token payload`

При этом Unsloth Desktop работал, а локальный список моделей был доступен.

## Диагностика

1. `~/.hermes/config.yaml` указывал на `provider: unsloth`, модель `qwen35-4b`, endpoint `http://127.0.0.1:8888/v1`.
2. Запрос `GET /v1/models` с ключом из активного раздела `model` вернул HTTP 200.
3. В конфигурации профиль `providers.qwen3.5-4b` ссылался на переменную окружения:
   `HERMES_CUSTOM_127_0_0_1_8888_API_KEY`.
4. При чтении `~/.hermes/.env` выяснилось, что эта Custom-переменная содержала значение длиной 4 символа, тогда как рабочий ключ в активной конфигурации имел длину 43 символа. Сами значения нигде не выводились.
5. Проверка `GET /v1/models` с Custom-переменной вернула HTTP 401; с рабочим ключом — HTTP 200.

## Исправление, которое сработало

- До изменения проверили рабочий ключ через локальный endpoint.
- Создали резервную копию `~/.hermes/.env` с правами доступа `0600`.
- Обновили только переменную `HERMES_CUSTOM_127_0_0_1_8888_API_KEY`, скопировав уже проверенный рабочий ключ из активного раздела `model`.
- Установили права доступа `0600` на `~/.hermes/.env`.
- Полностью закрыли и заново запустили Hermes Desktop.
- Визуальный Hermes ответил на контрольный запрос `Ответь ровно: HERMES_RECOVERY_OK` — восстановление подтверждено.

Резервная копия осталась в `~/.hermes/.env.backup-YYYYMMDD-HHMMSS` (фактический файл на этой машине создан 2026-10-10). Не публиковать этот файл: в нём могут быть секреты.

## Урок на будущее

HTTP 200 на `GET /v1/models` подтверждает авторизацию только для того ключа, который использован в этом конкретном запросе. Hermes Desktop и отдельный Custom-профиль могут использовать другую переменную окружения, даже когда основной профиль CLI выглядит исправным.

При `Custom rejected your API key` / `Invalid token payload`:

1. Не переустанавливать Hermes и модели сразу.
2. Проверить endpoint и ключ основного профиля, не показывая значения ключей.
3. Найти имя переменной `key_env`, которую использует нужный Custom-профиль.
4. Проверить наличие и доступность именно этой переменной.
5. Если найдено расхождение, сохранить backup, обновить только подтверждённо неверную переменную, затем перезапустить приложение и выполнить короткий тестовый запрос.

**Не выводить API-ключи в терминал, отчёты или GitHub.** Не копировать ключи между профилями без предварительной успешной проверки рабочего источника.

## Статус компонентов

- Unsloth API: PASS (`GET /v1/models` вернул HTTP 200 с рабочим ключом).
- Hermes Desktop → Unsloth после исправления и перезапуска: PASS (`HERMES_RECOVERY_OK`).
- Полная цепочка голоса STT → LLM → TTS: этим тестом НЕ проверялась.

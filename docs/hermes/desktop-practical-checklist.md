# Hermes Desktop: практический пошаговый чек-лист

Эта инструкция адаптирована под наш локальный Ubuntu-стек. Она опирается на два материала Хабра и отделяет примерные настройки автора от нашего фактического состояния.

## Источники

- [Hermes Agent Desktop: личный опыт и пошаговая настройка](https://habr.com/ru/articles/1044270/)
- [Hermes Agent сжигал 603M токенов за спиной — оптимизация auxiliary](https://habr.com/ru/articles/1042860/)
- [Официальная документация Hermes Agent](https://github.com/NousResearch/hermes-agent)
- [Официальное описание Voice Mode](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/voice-mode.md)

В статье про Desktop часть примеров дана для Windows/WSL и конкретной версии. Названия и расположение элементов нашего Linux UI могут отличаться. Не копируйте чужой YAML целиком.

## Наша исходная точка

- Hermes Desktop установлен и работает.
- Команда `unsloth start hermes --app` выполнена.
- Текстовый запрос через Unsloth успешно проверен контрольной строкой.
- Основная модель через Unsloth: Qwen3.5-4B Q4_K_M.
- Qwen3-ASR-0.6B хорошо распознаёт речь в Unsloth, но ещё не подключена к Hermes напрямую.
- В Hermes Voice были включены Speech-to-Text и подтверждение/проверка транскрипции; язык транскрипции не был задан.
- В конфигурации ранее выполнялась команда `hermes config set compression.enabled false` из-за ошибки с контекстом. После смены маршрута необходимо отдельно проверить, подходит ли это состояние для новых сессий.

## 1. Model

Что делать:
1. Открыть Model.
2. Убедиться, что основной provider — подключённый Unsloth, а модель — та, которую выбрали в Unsloth.
3. Для Context Length оставить Auto/0, если сервер правильно сообщает контекст и нет необходимости задавать клиентский предел вручную.
4. Не задавать число больше реального контекста работающего сервера. Поле в Hermes не увеличивает серверный контекст.
5. После выбора другой модели в Unsloth повторно выполнить `unsloth start hermes --app`, как предписывает справка установленной версии, затем проверить новую сессию.

### Auxiliary Models

Вспомогательные задачи — отдельные вызовы: compression, web extraction, vision, skills hub, title generation, approval и другие, в зависимости от версии. Они не являются основным ответом чата.

Рекомендации:
- не оставлять маршрутизацию неосознанно на `auto`, если неясно, какая модель в итоге используется;
- назначать модели по задаче только после проверки совместимости;
- для compression нужна модель/endpoint с контекстом, удовлетворяющим требованиям текущей версии Hermes;
- не переносить из статьи провайдеры `ollama-cloud`, модели Kimi, RNJ или Qwen-VL в нашу локальную конфигурацию — это чужая облачная установка;
- после правки открыть новую сессию или перезапустить приложение способом, поддерживаемым текущей версией.

Не настраивать все auxiliary-задачи сразу. Сначала довести основной текстовый маршрут и голосовой ввод до стабильного состояния.

## 2. Chat

- Для коротких рабочих ответов выбрать краткий стиль Personality, если такой переключатель доступен.
- Reasoning Blocks управляет отображением рассуждений в UI; он не увеличивает и не уменьшает серверный контекст автоматически.
- Для запросов к компактным локальным моделям просить краткие результаты и выдавать им небольшие задачи. Не просить повторять длинные внутренние рассуждения.

## 3. Appearance

- Тема и цветовые акценты — только внешний вид.
- Tool Call Display: Technical полезен для диагностики (показывает аргументы инструментов); Product удобнее в повседневной работе.
- Эти настройки не меняют модель и её контекст.

## 4. Workspace

Для проектной работы:
- указывать нужный Working Directory (для базы Robot Factory OS это может быть `~/robot-factory-os`; для отдельного сайта — папка самого сайта);
- запускать код в режиме проекта, если нужен доступ к проектным файлам;
- не включать автоматическое подтверждение записей/команд без необходимости;
- включить редактирование с резервными копиями/контроль через Git, если опция доступна;
- скрывать секреты и не помещать API keys в промпты или репозиторий;
- переменные окружения вроде PATH/CUDA_PATH настраивать только когда конкретный инструмент их требует. Значения из Windows-гайда не переносить вслепую в Ubuntu.

## 5. Memory & Context

- Persistent Memory и User Profile можно включать, если хотим переносить полезные предпочтения между сессиями.
- Context Engine / Auto-Compression должны рассматриваться вместе с настройкой Auxiliary → compression.
- Если compression отключена, длинные сессии могут упереться в предел контекста, даже если первые запросы работают.
- Перед включением compression убедиться, что назначенный endpoint реально поддерживает минимальный контекст, который требует текущая версия Hermes.
- Не вводить в поле контекста число по максимальному training context из карточки модели. Проверять значение API работающего сервера.

Для нашего оборудования: RTX 3060 12 GB VRAM и около 11 GiB RAM. При Qwen3.5-4B наблюдалось 11,425/12,288 MiB VRAM. Не запускать параллельно дополнительную тяжёлую GPU-модель без замера.

## 6. Voice — наша цель: голосовой локальный помощник

Voice содержит несколько независимых компонентов:

- Voice Chat Mode: `Chained` или `GPT Live`/duplex варианты.
- STT — превращение речи в текст.
- Основная LLM — понимает команду и формирует ответ.
- TTS — произносит текст ответа вслух.

Для модульной локальной цепочки логично начать с `Chained`, но он не означает, что все компоненты автоматически локальные.

Практический порядок:
1. Включить Speech-to-Text.
2. Включить проверку/подтверждение транскрипции.
3. Установить язык Russian/Русский, если поле есть.
4. Сначала проверить встроенный локальный Whisper Hermes на короткой фразе.
5. Отдельно проверить Read Responses Aloud / TTS и выбрать реально доступного провайдера и голос.
6. Затем исследовать подключение уже проверенного Qwen3-ASR-0.6B через API Unsloth. Сейчас это отдельная интеграционная задача: само распознавание в Studio не означает, что Hermes обращается к нему.
7. Избегать двух приложений, одновременно захватывающих микрофон через горячие клавиши — это может создавать конфликт.

`GPT Live` может требовать отдельный совместимый real-time API. Не считать его локальным только потому, что основная LLM работает на компьютере.

## 7. Advanced

Не изменять лимиты и автономность без необходимости. Настройки вроде Max Agent Steps, command timeout, terminal output limit и parallel subagents влияют на поведение агента, а не заменяют качественную модель или корректное окно контекста.

Начать с безопасных значений по умолчанию. Если агент регулярно не успевает закончить задачу, сначала проверить логи и причины, а затем менять один параметр за раз.

## 8. Проверка после изменений

После смены модели/провайдера:
1. Создать новую сессию.
2. Отправить короткий текстовый тест — например, `Ответь ровно: HERMES_TEXT_OK`.
3. Проверить, что реально выбран Unsloth, а не старый provider.
4. Отдельно проверить голосовую транскрипцию короткой русской фразой.
5. Отдельно проверить озвучивание короткого ответа.
6. Только после этого дать настоящую задачу.

## 9. Оптимизация фоновых вызовов: что можно взять из второй статьи

Статья показывает, что auxiliary-задачи могут вызывать модель чаще, чем кажется, и что назначение отдельной модели на лёгкую задачу может улучшить экономику и задержку. Для локального компьютера аналогичная проблема — переключения моделей и давление на VRAM, а не только стоимость токенов.

Наш принцип:
- одна основная модель для общения;
- легковесные auxiliary только если они работают стабильно и не вызывают перегрузку памяти;
- не держать параллельно несколько больших локальных моделей;
- измерять фактическую пользу, а не просто заполнять каждое поле.
